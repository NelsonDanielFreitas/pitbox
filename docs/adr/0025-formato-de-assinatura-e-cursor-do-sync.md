# 0025 — Assinatura das operações, cursor do Pull e deteção de conflitos

- **Estado:** Proposto (aguarda confirmação do Nelson)
- **Cartão:** F1-13
- **Relacionado:** [ADR 0003](0003-app-offline-first-sync-proprio.md), [ADR 0018](0018-base-local-web.md), [ADR 0023](0023-extensoes-locais-do-inventario.md), [ADR 0024](0024-extensoes-locais-dos-setups.md); arquitetura §5.2 e §8; ameaças TM-SYNC-01..06, TM-DEV-02.

## Contexto

O ADR 0003 fixa o protocolo (`Push`/`Pull`, `op_id`, assinatura ECDSA por dispositivo, passe de 72 h, merge por campo) mas deixa por definir três pormenores que, mal resolvidos, quebram a segurança ou perdem dados:

1. **O que exatamente se assina.** Assinar um `Struct` obriga o cliente (JS) e o servidor (Go) a produzir os mesmos bytes de JSON canónico. Há diferenças reais: escape de `<`, `>`, `&`, U+2028/2029, ordem de chaves por UTF-16 vs UTF-8, formatação de números.
2. **O cursor do Pull.** `sync.change_log.seq` é `IDENTITY`: o valor é atribuído ao inserir, mas a transação só fica visível ao fazer *commit*, e as transações fecham fora de ordem. Um cliente que guardou `cursor = N` pode nunca ver uma linha com `seq < N` que fechou depois.
3. **Como saber que campos mudaram desde a `base_version`.** As tabelas de equipa só têm um contador `version`, sem histórico por campo.

## Decisão

1. **Assinatura sobre bytes, não sobre estrutura.** A operação leva `fields_json` (bytes UTF-8, objeto JSON, ≤ 64 KiB) e a assinatura cobre SHA-256 desses bytes exatos. A mensagem assinada (`SigningMessage`) é a etiqueta `pitbox-sync-op-v1` seguida de campos com prefixo de comprimento (`uint32` big-endian): `op_id`, `team_id`, `device_id`, `entity`, `entity_id`, `kind`, `base_version` (−1 se ausente), `client_ts` em milissegundos e o hash. O prefixo de comprimento torna a codificação injetiva; `team_id` e `device_id` impedem repetir a operação noutra equipa ou com outra chave. Algoritmo: ECDSA P-256 + SHA-256, assinatura IEEE P1363 (r‖s, 64 bytes), que é o que o WebCrypto produz. O servidor só aceita chaves P-256 em SPKI DER.
2. **Cursor sem buracos: `(xid, seq)`.** `sync.change_log` ganha `xid xid8 DEFAULT pg_current_xact_id()` e o índice `(team_id, xid, seq)`. O `Pull` só devolve linhas com `xid < pg_snapshot_xmin(pg_current_snapshot())` (transações já terminadas), **ordenadas e paginadas por `(xid, seq)`**, e o cursor opaco (`v1.` + base64url de `xid:seq`) guarda os dois. Só o filtro por `xid` não chega: uma transação antiga (xid 90) pode comitar uma linha com `seq` alto antes de outra mais recente ainda aberta (xid 100) comitar um `seq` mais baixo, e um cursor só por `seq` saltaria essa linha. Ordenando por `xid`, tudo o que comitar depois tem `xid` maior do que qualquer linha já devolvida. O parse do cursor só aceita a forma canónica. Custo: uma alteração só aparece no Pull depois de todas as transações mais antigas fecharem (milissegundos, ou mais se houver uma transação longa). Há um teste com uma transação deliberadamente aberta (e uma verificação de que falha sem o filtro).
3. **Conflitos pelo histórico de operações.** Como a app nunca chama a API diretamente (regra 7), todas as escritas de dados chegam como operações. `sync.operation` ganha `result_version` (versão da entidade depois da operação). Uma operação `PATCH` com `base_version = b` compara os seus campos com os das operações aplicadas com `result_version > b` na mesma entidade: mesmo campo com valor diferente gera `sync.conflict`; os restantes campos aplicam-se (um campo em conflito não bloqueia os outros). Valores iguais não são conflito. Acrescentos nunca entram em conflito.
4. **`client_ts` é assinado, mas não autoriza.** Nunca ordena operações. O servidor só o usa para recusar horas no futuro (> 5 min de desvio) e operações feitas depois de o passe expirar (+ 5 min); um dispositivo malicioso pode mentir sobre ele, o que é risco residual coberto pela revogação do dispositivo (TM-DEV-02). O passe é aberto pela assinatura sem exigir validade, porque um passe expirado ainda vale para operações feitas antes de expirar (nenhum dado perdido por passar mais de 72 h sem rede). A validade do passe é calculada pelo relógio da base de dados.
5. **Prova de posse no registo.** `RegisterDevice` exige uma assinatura da chave nova sobre `(team_id, user_id, chave pública)`, para ninguém registar uma chave que não possui.
6. **Assinatura guardada.** `sync.operation.device_signature` (64 bytes, `CHECK`) fica como prova de origem (TM-SYNC-01, repúdio).
7. **Rejeição não falha o RPC.** Cada operação tem o seu resultado (`applied|merged|conflict|rejected` com um código estável); um erro de uma operação não impede as seguintes, e o `op_id` já visto devolve o resultado guardado.

8. **Entidades sincronizáveis e aplicadores.** Cada módulo expõe no seu `api.go` os aplicadores das suas entidades (contrato em `platform/syncapply`); uma entidade sem aplicador não é sincronizável (lista de permissões). O aplicador valida tudo outra vez (o dispositivo não é de confiança): chaves desconhecidas são recusadas (sem *mass assignment*), tipos estritos, `null` limpa um campo opcional e a ausência não toca nele. O autor é sempre o utilizador autenticado, nunca um campo. Entidades desta fase:
   - `garage.car`: criar, editar, apagar (com as mesmas regras do caso de uso: catálogo ativo, montagem aberta).
   - `setup.setup`: só criar, já com a versão 1 (renomear não existe na API do servidor).
   - `setup.setup_version`: o `entity_id` é o id do **setup**; um `PATCH` com `base_version = N` significa «gravar uma nova versão baseada na N». Uma base desatualizada é conflito (ADR 0024). Como as versões são imutáveis, o campo `data` conta como um único campo no merge. O `Pull` desta entidade devolve as últimas 20 versões do setup.
   - `garage.engine`: criar e editar (`make`, `model`, `serial_number`, `purchased_on`, `status`, `notes`); recusa abater um motor montado. Os contadores são só do servidor.
   - `garage.tyre_set`: criar e editar (`label`, `make`, `model`, `compound`, `insert_type`, `glued_on`, `status`, `wear_notes`). Referências a peças de stock (cola) não são aceites aqui; chegam com os movimentos.
   - `garage.part`: criar, editar e abater (`delete`, que também tira a linha da lista de compras). A quantidade **não** viaja na peça: vem só dos movimentos de stock. O preço (`unit_cost_cents`) só é devolvido no Pull a `owner` e `mechanic` (ADR 0023) e, quando falta no payload, a app não apaga o valor local.
   - `garage.stock_movement`: só acrescentar (`append`); o `id` do dispositivo é a chave primária. Campos: `part_id`, `qty_delta_centi`, `reason`, `note`, `occurred_at`, `unit_cost_cents` (só compras), `loss_reason` (só perdas). Mesmas regras do `AddStockMovement` (sinal por motivo, preço, motivo de perda), com o bloqueio da peça para o stock «antes» ser exato; depois aplica os mesmos efeitos (evento de stock baixo; uma compra tira a linha da lista de compras e uma linha escondida volta quando o stock chega ao mínimo). Um `id` repetido é recusado e nunca duplica o stock. `occurred_at` do dispositivo só vale entre −90 dias e +5 min; fora disso fica a hora do servidor. A loja (só local) segue dobrada na `note` («Loja: X · nota») e um «desfazer» segue como um ajuste simples, sem `reverts_movement_id` (o outro dispositivo não vê o movimento como desfeito). O preço pago não é devolvido no Pull a pilotos e convidados.
   - `garage.shopping_item`: criar, editar e apagar (`part_id`, `qty_centi`, `dismissed`, `note`). Uma linha por peça: uma segunda criação para a mesma peça é recusada, e no Pull a linha do servidor substitui uma local com outro `id`. Uma linha visível precisa de quantidade efetiva positiva (a própria ou a sugestão). Uma linha não muda de peça.
   - `setup.setup_feedback`: só `append`; o piloto também escreve (ADR 0026, `syncapply.RoleGated`). O autor é sempre o utilizador autenticado.
   - As **contagens de inventário** não têm entidade: o rascunho é só local (ADR 0023) e aplicar a contagem gera movimentos de ajuste, que são os que sincronizam.
   - `garage.engine_mount`: criar (aberta: `engine_id`, `car_id`, `mounted_at`) e fechar (`Patch` com `unmounted_at`). Não tem coluna de versão: `CurrentVersion` devolve sempre 1 e fechar uma montagem já fechada é um sucesso sem efeito, por isso uma base desatualizada nunca gera conflito. Regras de `MountEngine`: motor e carro existem, não estão abatidos e não têm outra montagem aberta; uma sobreposição com o histórico é a restrição de exclusão da base de dados e volta como referência inválida. `mounted_at` e `unmounted_at` são do dispositivo (o mecânico montou o motor na pista, não quando o telemóvel apanhou rede), dentro da janela de −90 dias a +5 min; um fecho que não fica depois do início usa a hora do servidor.
   - `garage.part_install`: criar (`part_id`, `car_id` ou `engine_id`, `installed_at`) e fechar (`Patch` com `removed_at`, `removal_destination`, `removal_reason`), com as regras de `InstallPart`/`RemovePart` (peça com vida útil, alvo não abatido, destino/motivo coerentes). Fechar uma instalação já fechada é um sucesso sem efeito. **O movimento de stock não é criado aqui**: a app envia `installed` e `returned` como operações `garage.stock_movement` próprias, senão a unidade saía do stock duas vezes. A nota da instalação é só local.
   - **Limitação conhecida**: dois dispositivos que retiram a mesma peça para o stock offline enviam dois movimentos `returned` (a segunda retirada não faz nada, mas o seu movimento aplica-se) e o stock sobe 2. O mesmo vale para uma montagem criada em dois dispositivos para o mesmo motor: a segunda é recusada e a entidade local fica «fantasma» até ser apagada pelo Pull (a montagem do servidor substitui-a).
   - Já não há tabelas «ainda por sincronizar»: o logout só recusa apagar a base local por haver operações pendentes ou um rascunho de contagem aberto (só existe neste dispositivo, ADR 0023; `app/src/sync/logout-guard.ts`).
   - Ao migrar a base local, as linhas que só existiam localmente entram na fila: motores, pneus e peças como `create` (`0009_sync_backfill.sql`), depois os movimentos de stock (por ordem) e as linhas de compras das peças ativas (`0010_sync_inventory_backfill.sql`) e, por fim, as montagens e instalações, com cada fecho antes da montagem seguinte do mesmo motor ou carro (`0011_sync_mounts_backfill.sql`). Peças arquivadas ficam de fora: o servidor nunca as conheceu.

## Alternativas consideradas

| Alternativa | Motivo para rejeitar |
| --- | --- |
| Assinar JSON canónico (RFC 8785) | Exige implementações idênticas em Go e JS e continua sensível a casos extremos de Unicode e números. |
| Bloqueio consultivo por equipa nas escritas | Serializa todas as escritas da equipa para evitar o buraco do cursor; mais simples, mas limita a escala e bloqueia o modo final. |
| Cursor por *timestamp* | Relógios e *commits* fora de ordem têm o mesmo problema, pior. |
| Tabela de histórico por campo em cada entidade | Muito esquema para pouco ganho; o registo de operações já tem os valores. |
| Ed25519 para os dispositivos | O WebCrypto só o tem em versões recentes e o armazenamento seguro nativo (Keystore/Secure Enclave) suporta P-256 de forma universal. |

## Consequências

- Migrações `…f1-13-sync-signature-and-cursor.sql` (`device_signature`, `result_version`, `xid`, índice de merge) e `…f1-13-change-log-cursor-index.sql` (índice `(team_id, xid, seq)`, `CONCURRENTLY`).
- Limitação conhecida: resolver um conflito escreve o valor sem criar uma operação, por isso um `PATCH` atrasado posterior não o vê como alteração.
- A fonte de verdade do formato é `backend/internal/sync/domain/signing.go`; o cliente tem de a replicar e há testes de vetores em ambos os lados.
- Uma operação só é «aplicada» depois de aplicada à entidade de destino; se o aplicador falhar, a linha de `sync.operation` não fica com `result_version`.
- Alterações futuras ao formato mudam a etiqueta (`…-v2`) e aceitam as duas durante a migração (agilidade criptográfica).
- Fora do âmbito: sync local na box por BLE/rede local (fase 2), *stream* do servidor para o Pull (depois), purga das lápides com mais de 30 dias (job River, cartão a propor).
